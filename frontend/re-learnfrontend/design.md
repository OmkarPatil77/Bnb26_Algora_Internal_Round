# Product UI and Anti-AI-Slop Design Rules

## Core Principle

Build interfaces that look like they were designed and engineered by a professional product team, not generated by an AI website builder.

The result must feel intentional, restrained, credible, and specific to the actual product.

Do not optimize for "impressive AI-generated visuals." Optimize for clarity, usability, authenticity, and product relevance.

## ABSOLUTE DESIGN RESTRICTIONS

Never use the following unless the user explicitly requests them:

- Purple-to-blue gradients
- Generic neon gradients
- Excessive glassmorphism
- Excessive blur effects
- Pill-shaped UI elements everywhere
- Giant rounded cards containing every section
- Floating cards with arbitrary shadows
- Generic dashboard boxes
- Decorative blobs
- Random geometric background shapes
- AI-generated-looking 3D objects
- Generic AI illustrations
- Fake product screenshots
- AI-generated stock-style photography
- Emoji used as UI icons
- Random Lucide/icon-library icons used merely for decoration
- Fake testimonials
- Fake reviews
- Fake ratings
- Fake customer counts
- Fake user counts
- Fake revenue numbers
- Fake performance metrics
- Fake logos
- Fake partner/company logos
- Fake case studies
- Fake social proof
- "Trusted by 10,000+ users" style claims unless backed by real data
- "Join 50,000+ users" style claims unless backed by real data
- Invented statistics
- Invented achievements
- Invented customer names
- Invented company names
- Invented reviews
- Invented credentials
- Invented certifications

## CONTENT RULES

Never invent product facts.

Never create placeholder marketing claims that look real.

Never write vague hero copy such as:

"Transform your workflow."
"Unlock the future."
"Reimagine what's possible."
"Where innovation meets simplicity."
"Powering the next generation."
"Build smarter. Move faster."

Hero copy must explain the actual product, user problem, or value proposition in concrete language.

Use specific product language instead.

If real content is unavailable, use clearly identifiable placeholders rather than fabricated facts.

For example:

GOOD:
"[Product description goes here]"

BAD:
"Trusted by 10,000+ professionals worldwide."

Never fabricate metrics simply to make a page look complete.

## TYPOGRAPHY

Use typography deliberately.

Prefer:

- Clear hierarchy
- Strong readable headings
- Comfortable body text
- Limited font families
- Appropriate line lengths
- Consistent spacing

Do not make every heading enormous.

Do not use typography purely to create visual drama.

## BUTTONS

Buttons should look like real product UI.

Do not make every button pill-shaped.

Prefer modest border radii appropriate to the surrounding design.

Use clear action-oriented labels:

GOOD:
"Create itinerary"
"View details"
"Start application"
"Generate report"

BAD:
"Let's Go!"
"Explore the Magic"
"Unlock Your Journey"

Do not add unnecessary buttons.

Every button must have a real purpose and working interaction.

## CARDS AND CONTAINERS

Do not put everything inside cards.

Use cards only when they provide meaningful grouping or interaction.

Avoid the common AI-generated pattern:

[ huge rounded card ]
[ icon ]
[ huge heading ]
[ paragraph ]
[ button ]

repeated across the entire page.

Use normal sections, grids, lists, tables, dividers, typography, whitespace, and other appropriate layout primitives.

Visual hierarchy should come from spacing, typography, alignment, and structure rather than excessive containers.

## ICONS

Icons must communicate something meaningful.

Do not place an icon above every heading just to fill empty space.

Do not use emoji as interface icons.

Use an existing icon library only when the icon has a clear semantic purpose.

When an icon is unnecessary, do not add one.

## ANIMATION

Animation must have a functional purpose.

Do not use:

- Cursor-following effects
- Fake cursor animations
- Mouse-tracking gradients
- Excessive parallax
- Scroll-triggered animations everywhere
- Text scrambling
- Random floating elements
- Continuous decorative motion
- Excessive entrance animations

Prefer subtle transitions for:

- Hover states
- Focus states
- Expanding/collapsing content
- Modal transitions
- Navigation changes
- Meaningful state changes

The interface should still feel complete with animations disabled.

## HERO SECTIONS

Do not create a generic AI SaaS hero.

Do not use:

- Massive empty hero sections
- Huge gradient text
- Decorative 3D graphics
- Fake dashboard screenshots
- Generic AI imagery
- Floating UI fragments
- Vague one-line slogans

The hero must communicate:

1. What the product is
2. Who it is for
3. What problem it solves
4. The primary action

Keep it concise and specific.

## IMAGES

Do not use AI-generated-looking imagery unless explicitly requested.

Do not add images simply because the page "needs visuals."

If imagery does not provide meaningful product or contextual value, use layout, typography, diagrams, real screenshots, or actual product UI instead.

If real images are required but unavailable, use clearly marked placeholders rather than fake-looking imagery.

## RESPONSIVE DESIGN

Every page must work properly on:

- Mobile
- Tablet
- Desktop

Do not solve responsive design by simply shrinking desktop elements.

Check:

- Navigation
- Typography
- Grid behavior
- Spacing
- Buttons
- Forms
- Tables
- Images
- Overflow
- Touch targets

## ACCESSIBILITY

Use:

- Semantic HTML
- Proper heading hierarchy
- Keyboard navigation
- Visible focus states
- Accessible labels
- Sufficient contrast
- Meaningful alt text
- Proper form labels

Do not sacrifice accessibility for visual effects.

## PRODUCT AUTHENTICITY

Before adding any section, ask:

"Does this represent a real product requirement?"

If the answer is no, do not add it merely to make the website look more complete.

Do not manufacture:

- Reviews
- Testimonials
- Statistics
- Customer logos
- Metrics
- Awards
- Integrations
- Certifications
- Usage numbers

## PRE-LAUNCH REQUIREMENTS

Do not consider the website production-ready until these have been addressed:

- Custom domain connected
- Favicon added
- Page title configured
- Meta description configured
- Open Graph metadata configured
- "Made with AI" / generator branding removed where legally and technically possible
- Privacy Policy page added
- Terms and Conditions page added
- 404 page handled
- Responsive layout verified
- Forms verified
- Navigation verified
- External links verified
- Console errors resolved
- Broken images resolved
- Placeholder content removed
- Fake data removed or clearly marked as demo/synthetic data
- Accessibility basics checked

If custom domain, legal pages, or other deployment requirements cannot be completed from the current environment, explicitly report them as remaining tasks instead of pretending they are complete.

## DATA INTEGRITY

If demo/synthetic data is required for a prototype, clearly distinguish it from real data.

Use labels such as:

"Demo data"
"Synthetic dataset"
"Prototype"
"Sample data"

Never present synthetic data as real-world statistics.

## CODE QUALITY

Do not create unnecessary components merely to make the code appear sophisticated.

Do not introduce unnecessary dependencies.

Reuse existing components and design tokens where appropriate.

Before adding a new UI pattern, inspect the existing application and maintain visual consistency.

Do not rewrite working parts of the application unnecessarily.

## BEFORE IMPLEMENTATION

Before building a significant UI, inspect the existing codebase and determine:

- Existing design system
- Existing components
- Existing typography
- Existing spacing
- Existing color tokens
- Existing icon system
- Existing routing
- Existing responsive patterns

Extend the existing system instead of inventing a completely new visual language.

## FINAL UI REVIEW

Before declaring the task complete, perform a visual and functional review.

Check specifically for:

- Purple gradients
- Generic AI aesthetics
- Excessive rounded cards
- Excessive pill buttons
- Fake metrics
- Fake testimonials
- Fake reviews
- Fake logos
- Vague marketing copy
- Emoji icons
- Decorative icons with no purpose
- Unnecessary animations
- Cursor effects
- AI-generated imagery
- Placeholder content
- Broken interactions
- Mobile layout problems
- Console errors
- Missing favicon
- Missing legal pages
- Generator/AI branding

If any of these are present without explicit justification or user instruction, fix them before completing the task.

## MOST IMPORTANT RULE

Do not try to make the website "look impressive."

Make it look like a real product.

Specific > generic.
Useful > decorative.
Authentic > flashy.
Intentional > excessive.
Functional > animated.

When uncertain, choose the simpler and more product-specific solution.

# Project boundaries (Re:Learn)

Three layers: /src (frontend), /backend (Node + Express + MongoDB), /ml (Python, built by a teammate).

- Never edit model code, training code, datasets or weights in /ml. If /ml needs a change, write it in docs/ML_REQUESTS.md instead.
- Create a thin /ml/service.py (FastAPI) only if /ml has no HTTP interface yet. It may only wrap existing functions.
- Backend talks to ML over HTTP only. Frontend talks to the backend only, through src/services/api.ts.
- Do not duplicate logic across layers. Diagnosis and probe selection live in /ml. Learner model and resolution rule live in /backend.
- docs/API_CONTRACT.md is the single source of truth. Change the contract first, then the code.
- Never invent data. Anything synthetic or from the mock adapter must be labeled "Demo data" in the UI.
- Do not change UI components except to fix a contract mismatch, unless the task is explicitly a UI pass.
- Work on one layer per task. Stop and show the plan before writing code.
